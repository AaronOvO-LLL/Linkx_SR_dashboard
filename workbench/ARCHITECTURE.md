# 灵石解决方案工作台架构说明

> 状态：生效中  
> 适用范围：`workbench/` 下的应用代码、产品配置、模板、数据库和测试  
> 架构目标：在保持单机 Flask 部署简单性的前提下，使产品、输入方式、外部厂商和生成物可以独立增减。

## 1. 架构原则

本项目采用**模块化单体**，暂不拆分微服务。浏览器、Flask 进程、SQLite 和文件输出仍部署在一起，但代码必须遵守以下边界：

1. Web 路由只处理 HTTP、会话、参数和页面跳转，不编写业务规则。
2. `services/` 表达一个完整业务动作，例如“保存文字稿并开始提取”。它负责事务顺序和跨模块编排。
3. `core/` 保存稳定的领域能力和基础设施，不依赖 Flask 的 `request`、`session` 或模板上下文。
4. `providers/` 隔离腾讯云等外部厂商。业务层只依赖接口，不直接依赖厂商 SDK。
5. `config/products/<product_type>/` 保存产品差异；公共 Python 代码不得用产品名写分支。
6. 数据库结构只能通过迁移演进，不能依赖人工修改现有数据库。
7. 能力必须显式声明。产品没有声明某能力时，页面和服务都不能假设它存在。
8. 录音转写属于**项目级**资产，不属于任何产品。一份录音只转写一次，转写稿由项目下各产品共同引用。

依赖方向固定为：

```text
templates / routes
        ↓
     services
        ↓
core domain + repositories
        ↓
 database / providers / filesystem
```

下层不得反向导入上层。例如 `core/` 不得导入 `app.py`，provider 不得调用页面函数。

## 2. 技术栈

| 层次 | 技术 | 约束 |
|---|---|---|
| Web | Python + Flask + Jinja2 | 路由保持薄，页面不承担业务判定 |
| 前端 | 原生 HTML/CSS/JavaScript | 当前规模不引入前端框架；复杂媒体交互出现后再单独评估 |
| 数据 | SQLite，WAL 模式 | 所有结构变化必须登记迁移；业务代码通过 repository 访问 |
| 配置 | JSON + Jinja 模板 | 产品差异优先配置化，但配置必须有校验器和版本号 |
| 对象存储 | provider 接口，首个实现为腾讯 COS | 私有桶、短时签名 URL；不得把永久公网地址写入数据库 |
| 语音识别 | provider 接口，首个实现为腾讯云 ASR | 异步任务、可恢复、幂等提交；音频按临时对象管理 |
| 结构化梳理 | DeepSeek OpenAI 兼容接口 | 密钥仅来自环境变量；模型输出仍须通过字段校验与人工核对 |
| 测试 | `unittest` + Flask test client + 端到端自测 | 每次变更至少执行配置检查、单元测试和主流程自测 |

密钥只允许从环境变量读取，不得进入 JSON、数据库、日志、示例命令或截图。

## 3. 关键目录和文件职责

### 3.1 Web 与服务层

| 路径 | 功能 | 不应承担 |
|---|---|---|
| `app.py` | Flask 初始化、路由、权限入口、HTTP 响应 | 字段提取规则、厂商调用、跨步骤业务编排 |
| `services/audio.py` | 项目级录音上传、异步转写、预览确认、共享转写稿 | 产品字段规则、把转写稿直接写进某个产品 |
| `services/survey.py` | 文字来源保存、导入项目转写稿、提取、字段确认 | HTML 渲染、直接读取 session |
| `services/artifacts.py` | 预览准备、生成、重试等生成物用例 | 具体模板内容和产品价格规则 |
| `templates/` | 页面表达 | 数据写入和业务状态计算 |
| `static/` | 页面样式与轻量交互 | 密钥、权限判定、最终业务校验 |

后续路由继续按领域拆分为 Blueprint 时，URL 和服务层接口保持不变，避免一次性重写。

### 3.1.1 项目级与产品级的职责分界

一次踏勘通常只录一份音，但可能同时评估多个产品。因此：

| 归属 | 数据 | 入口页面 |
|---|---|---|
| 项目级 | 录音文件、转写任务、确认后的共享转写稿 | `project.html`、`transcription.html` |
| 产品级 | 导入后的文字稿、字段值、校验、生成物、导出包 | `survey.html` 及其后续步骤 |

共享转写稿通过一次显式「导入」动作复制到产品的 `survey_sources`。复制而不是直接引用，是为了让每个产品可以独立微调文字、独立保留提取历史，互不覆盖。

### 3.2 核心层

| 文件 | 功能 | 关键约束 |
|---|---|---|
| `core/config.py` | 装载应用、产品、字段和生成物配置 | 不实现业务规则 |
| `core/runtime.py` | 部署运行时：模式判定与环境变量覆盖 | 真实密钥只从环境变量读，不回显、不落盘 |
| `core/departments.py` | 分部凭据：种子初始化、哈希校验与改密 | 明文口令不得写入运行时文件 |
| `core/capabilities.py` | 产品能力声明和校验 | 新模块必须先登记能力 key |
| `core/fieldmodel.py` | 字段包组装、覆盖、移除和契约校验 | 发布后的字段 key 不得改名 |
| `core/extract.py` | 文本到字段的提取器 | 产品提示词和特殊规则逐步迁到产品配置 |
| `core/validate.py` | 通用字段校验 | 产品专用跨字段规则不得长期写死在这里 |
| `core/generate.py` | 通用模板渲染与文件生成 | 不为某个 artifact key 增加硬编码分支 |
| `core/packaging.py` | 通用 ZIP、manifest 和 README | 不引用已经移除或未声明的能力 |
| `core/repo.py` | 数据访问和聚合查询 | 不处理 HTTP，不调用外部厂商 |
| `core/db.py` | 连接管理、基础表和迁移入口 | 不存业务流程代码 |
| `core/migrations.py` | 按版本、按顺序升级历史数据库 | 已发布迁移不得修改，只能新增迁移 |

### 3.3 产品配置

每个产品目录至少包含：

```text
config/products/<product_type>/
  product.json       # 产品身份、版本、能力声明
  fields.json        # 字段包组装清单
  artifacts.json     # 生成物清单
  templates/         # 生成物模板
  asr_terms.json     # 产品词表素材，仅供 tools/ 生成厂商热词表，运行时不读取
```

`product.json.capabilities` 是功能开关，也是依赖契约。当前允许的能力由 `core/capabilities.py` 统一定义。页面显示、服务调用和配置检查必须使用同一份声明。

ASR 运行时词表是**项目级**的，位于 `config/asr_terms.json`（`scope=project_global`）。转写发生在选择产品之前，此时无法确定产品，所以热词与术语纠错必须使用合并后的一份词表。产品目录下的 `asr_terms.json` 保留为词表素材来源，两者之间的合并目前是人工动作，存在漂移风险，后续应由 `tools/` 自动生成。

## 4. 新增或删除模块的接入方式

### 4.1 新增一个产品

1. 复制 `config/products/_template/`。
2. 填写产品身份和 `capabilities`，只声明已经具备配置与实现的能力。
3. 复用或新增字段包，禁止复制一份公共字段后各自漂移。
4. 增加生成物清单和模板。
5. 提供至少一份脱敏输入与期望字段结果。
6. 执行 `python check_config.py <product_type>` 和完整测试。

### 4.2 新增一种输入能力

以图片或音频为例：

1. 先判定归属：该输入是**项目级**（一次采集、多产品共用，如录音）还是**产品级**（各产品独立，如产品专属图片）。归属决定外键落在 `projects` 还是 `project_products`，事后迁移成本很高。
2. 在 `core/capabilities.py` 注册稳定的 capability key。
3. 在 provider 层定义接口与厂商实现。
4. 用数据库迁移增加通用资产或任务表。
5. 在 service 层实现上传、状态变化、重试和清理。
6. 路由只调用 service；模板根据 capability 决定是否显示入口。
7. 产品完成配置和验收后再打开 capability。

不得把 COS SDK 或 ASR SDK 调用直接写进路由。

### 4.3 新增一种生成物

普通 Markdown/HTML 生成物只增加 `artifacts.json` 条目和 Jinja 模板。若需要新的文件格式，应注册独立 renderer，而不是在 `generate.py` 中判断具体 artifact key。

### 4.4 删除一个模块

删除顺序固定为：

1. 从产品 capability 和生成物配置移除入口。
2. 删除页面和 route。
3. 删除 service 与 core 依赖。
4. 用迁移清理活动设置或记录；历史文件先备份，不在普通发布过程中直接物理删除。
5. 删除专用配置、模板、测试和演示数据。
6. 全局检索模块名及历史 key，确认没有运行时引用。

## 5. 数据库与状态管理

`core/db.py` 中的基础 schema 用于创建新数据库；`core/migrations.py` 负责把已有数据库升级到当前版本。迁移必须满足：

- 一个版本只执行一次；
- 在事务内执行，失败时整体回滚；
- 已发布迁移不可改写；
- 破坏性迁移先备份，并在发布说明中明确；
- 外部任务 ID、对象 key 和状态必须入库，不能只保存在内存中。

长任务状态建议统一为：`pending → running → success | failed | cancelled`。重试必须复用已存在的厂商任务或创建明确的新 attempt，避免刷新页面造成重复计费。

### 5.1 只读配置与运行时状态的边界

`config/` 是**只读**的：部署后服务进程不需要、也不应该有写权限（最小权限）。任何运行时会被应用改写的状态都必须落在 `data/` 下，因为该目录在服务器上归服务账户所有，且已被 `.gitignore` 排除，不会把用户数据带进代码库。

分部凭据是这条边界的唯一实例：`config/departments.json` 是只读种子（含初始口令），首次启动时由 `core/departments.py` 哈希后生成 `data/departments.json`，此后改密只写运行时文件。因此**改种子对已初始化的环境无效**，重置口令的手段是删除运行时文件让它按种子重建。新增可变配置时沿用同一模式，不要给 `config/` 开写权限。

## 6. 注释与文档规范

重要函数或功能必须增加注释，但注释重点解释**为什么这样做**，而不是复述代码。

以下位置必须写 docstring 或块注释：

- 跨模块的公共函数；
- 数据迁移及兼容逻辑；
- 权限和数据隔离边界；
- 外部厂商调用、重试、幂等和清理逻辑；
- 非直观的状态转换；
- 为防止数据丢失、重复计费或越权而存在的判断；
- 暂时保留的历史兼容字段。

推荐：

```python
def submit_once(asset_id):
    """同一资产只提交一次。

    页面刷新可能重复触发请求；先检查持久化任务 ID 可以避免 ASR 重复计费。
    """
```

不推荐：

```python
# 提交任务
submit_task()
```

需要这些注释的原因是：本项目的高风险并不在算法本身，而在数据生命周期、权限、外部计费和历史兼容。只描述“做了什么”的注释很快会与代码重复，解释“为什么”的注释才能保护后续修改者不误删关键约束。

## 7. 工作习惯与完成标准

每次变更遵守以下顺序：

1. 先更新契约或架构说明，再修改实现。
2. 小步提交，一个变更只解决一个主题。
3. 不把密钥、客户原始录音和未脱敏图片提交到代码库。
4. 修改字段时升 `template_version`；修改产品能力时升产品版本。
5. 修改数据库时新增迁移，并同时验证新库和历史库升级。
6. 删除模块时不顺手删除历史用户文件；数据清理由单独、可审计的动作完成。
7. 交付前运行：

```powershell
python check_config.py --strict
python -m unittest discover
python selftest.py
```

一次功能调整只有同时满足“配置通过、测试通过、页面主流程通过、文档同步”才算完成。
