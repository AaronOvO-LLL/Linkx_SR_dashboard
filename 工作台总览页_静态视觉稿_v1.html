B02

WHY要解决的问题

瓶颈不在人不够，而在信息从「口语」到「结构化」这一段全靠手工。

踏勘录音整理耗时2 小时现场录音，靠人工回听整理成踏勘表，通常要半天到一天。
口径不统一、漏填错填不同人填的踏勘表字段口径不一致，关键字段缺失要到写方案时才发现。
方案材料每次从零重写材料出得慢，商机响应就慢；同一份事实被反复誊抄进不同文档。

现状 → 目标

回听录音手敲表格→转写 + AI 提字段
各产品各填一遍公共信息→项目级录一次，多产品共用
字段口径靠个人经验→字段模型 + 校验规则约束
方案材料手工排版→模板渲染，一键生成打包
所以呢：这个工作台要替代的不是「踏勘」这件事，而是踏勘之后的信息结构化与材料生成这段纯手工劳动。

B04

FLOW核心业务流程

十个节点里只有两处必须人工：校对转写稿、补齐 / 确认字段。其余由平台自动完成。

1
分部登录选分部 + 口令，数据按分部隔离
2
项目中心建项 / 选项 / 复制 / 归档
3
项目概览基础信息、产品进度、项目级录音
4
录音转写上传 → 异步转写 → 人工校对 → 确认
5
调研输入粘贴文字稿或导入项目转写稿
6
信息核对AI 提字段 → 人工确认 / 补填
7
预览生成校验通过后渲染产出物
8
结果中心下载单文件或打包 ZIP
平台自动 必须人工介入 字段状态机：已提取 / 待确认 / 必须补填 / 可选缺失 / 已人工确认

两条设计红线

  • 一份录音只转写一次。录音与转写稿属于项目级资产，项目下各产品显式「导入」后各自微调，互不覆盖，也不重复计费。
  • 同一任务不重复提交。厂商任务 ID 入库，刷新页面不会重复触发 ASR 计费。

反幻觉约束

  • AI 提取必须附原文片段（quote），且 quote 必须是文字稿的真实子串，否则该字段降级为「待确认」。
  • 信息含糊时留空并标记待确认，不得编造默认值。
  • 人工确认过的字段受保护，重新提取不覆盖。
B05

DATA MODEL公共信息层与字段模型

字段模型 = 引用公共字段包 + 产品专属字段包 + 产品内组装覆盖。一次定义、多产品继承，禁止复制一份公共字段后各自漂移。

为什么要有公共层

  • 项目基本情况、项目资料、物业信息在所有管家里都要填一遍 —— 重复成本随产品数量线性放大。
  • 一次踏勘往往同时评估多个产品，公共事实只应录一次。
  • 公共字段口径改一处，所有产品同步生效。

B12

SECURITY安全与数据边界

本项目的高风险不在算法，而在数据生命周期、权限、外部计费与历史兼容。

已经做到的

  • 密钥只从环境变量读取，不进 JSON、数据库、日志、示例命令或截图。
  • config/ 只读、data/ 可写：分部口令种子哈希后落 data/departments.json，明文不写运行时文件。
  • .gitignore 覆盖敏感文件与运行数据；客户原始录音与未脱敏图片不入代码库。
  • 数据按分部隔离，跨分部不可见；改密只写运行时文件。
  • COS 私有桶 + 6 小时签名 URL，不存永久公网地址。
  • 数据库只通过迁移演进，已发布迁移不改写，破坏性迁移先备份。

需要盯住的

  • 录音能否上公有云：含客户敏感信息，若要「音频不出内网」需要本地 ASR 方案（待拍板，见 B15）。
  • ASR 词表漂移：运行时词表是项目级的，产品目录下是素材，两者目前靠人工合并。
  • SQLite 单写：并发写入能力有限，试点人数上来后需要评估。
  • 依赖未锁版本：已补 requirements-prod.txt，仍需固定完整锁文件。
  • 运行数据无清理策略：录音、转写稿、导出文件会持续累积。

  • Windows / Linux，Python 3.x
  • 项目自带 workbench/.venv（含 openpyxl 3.1.5）
  • 外部服务（可选）：腾讯云 ASR / COS、DeepSeek API Key

启动

# 方式一：双击启动脚本（Windows）
启动 Demo.bat
启动 生产模式测试.bat

# 方式二：命令行
cd workbench
.venv/Scripts/python.exe app.py
# → http://127.0.0.1:8770

需要拍板的三件事

① 录音能否上公有云含客户敏感信息。不决策的后果：无法确定是否需要「音频不出内网」的本地 ASR 方案，部署形态悬空。
② 域名备案进度不决策的后果：只能停在阶段一（公网 IP + HTTP），无法上 HTTPS。
③ 有无真实受控价格表当前演示单价为假设值，报价能力已停用。不决策的后果：不能对外说钱，价值卡片收益部分只能定性。
另有一条上线前硬性动作：5 个分部初始口令必须全部更换。
