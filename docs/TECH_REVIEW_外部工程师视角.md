## 一、先说清楚：这个系统承诺了什么

在评价代码之前先对齐承诺，否则后面的判断没有尺度。

| 项 | 内容 |
|---|---|
| **谁在用，用来做什么** | 一线同事把现场踏勘访谈（录音转写稿 / 文字稿）录进去，系统整理成结构化字段，再生成四类交付文档（踏勘结果、价值卡片、交付内容、提资清单），以及设备管家的传感器配置清单 |
| **什么结果算正确** | 字段值与访谈原文一致；缺失信息标「待确认」而不是编造；生成物中的结论能追溯到来源；数字（如传感器数量）按规则算对 |
| **出错的后果** | 生成的文档可能直接用于内部同步与客户沟通 → **错误结论会被当成事实传递**，可能引发错误报价、错误采购、客户信任损失 |
| **数据敏感度 / 可逆性** | 含客户项目信息、现场照片、访谈录音；项目可删除可复制，但生成物是**覆盖写**（见问题 5），历史版本不可恢复 |
| **谁维护，能投入多少** | 从提交记录与文档语气看，单人主导 + AI 辅助开发，投入有限 |
| **本次评审要回答的问题** | 这套系统能交付可信的文档吗？上线前必须改什么？ |

**风险画像结论**：团队内部日常依赖、数据含客户信息、**输出会向外传递**、单人兼职维护、已部署至公网（腾讯云 134.175.156.176）。

因此本次按**中等偏严格**标准评审——不是按个人工具，也不按对外 SLA 系统。**关键判定点落在「生成物是否可信」而不是「代码是否优雅」。**

## 四、做得好的地方（必须有行号）

### 1. 保守设计：宁可留空，不编造 —— 这是生成类系统最关键的一条

**我做了**：跑规则通道提取，并翻了几处边界处理。

```
$ python -c "... extract.cn2num('三栋')"       → None      【已复现】
$ python -c "... extract.cn2num('二十万')"      → 200000.0  【已复现】
$ python -c "... extract.negated('驻场暂时不需要','需要')" → True  【已复现】
```

`cn2num('三栋')` 返回 None——遇到非数字字符直接放弃，不猜。`negated` 处理否定语境。`core/extract.py:595 _normalize_llm_value` 的 docstring 写着「不合规值按缺失处理，禁止宽松落库」。`core/rules.py:282 _sensor_qty` 未知模式**直接抛错而不回落 1:1**。

**我的评价**：对一个「把口语转成正式文档」的系统来说，这条比性能重要得多。一个编出来的数字进了客户文档，代价远大于一个「待确认」。

### 2. 结论可追溯到来源

**我做了**：构造上下文看 `meta` 与字段级字段。

```
ctx['meta'] = {"generated_at":"2026-10-01 16:40","product_version":"0.3.0",
  "template_version":"0.2.0","field_template_version":"0.6.0",
  "rules_version":"","extraction_provider":"rule","source_chars":1137}   【已复现】
```

每个字段值还带 `source_quote`（原文引用）与 `confidence`。生成物里能回答「这个数字从哪句话来、按哪版规则算」。

### 3. 几个让我点头的决策

| 决策 | 位置 | 为什么我认可 |

## 五、风险与问题

> 每条按：**证据 → 失败机制 → 成立条件 → 结论与确定程度**。

### 问题 1：没有任何日志框架　【已复现】

- **证据**：`grep -rn "import logging|logging\.|logger" workbench/core workbench/services workbench/app.py workbench/providers` → **0 命中**；与之相对，`print(` / `print_exc()` 有 14 处（含 `core/generate.py:298`）。
- **失败机制**：系统连着两个**付费外部 API**（腾讯云 ASR 按分钟、DeepSeek 按 token）。若调用失败或计费异常 → 只有数据库里的最终状态和控制台输出 → **无法回答：哪次调用、耗时多少、失败原因、影响了哪个项目**。
- **成立条件**：只要出现一次账单争议或一次「用户说提取结果不对」的排查，就会暴露。
- **结论**：**建议修复**。这是我最坚持的一条——不是代码质量问题，是出事时拿不出证据。
- **确定程度**：【已复现】（命令结果为 0 命中）。

> 部署文档写的是 `journalctl -u lingshi-workbench` 看日志——但那只能看到 waitress 的访问与启动信息，看不到业务调用。

### 问题 2：没有 CI，体检靠人肉记着跑　【已复现】

- **证据**：`ls -a .github` → 无此目录。`check_config.py --strict`、`unittest`、`selftest.py` 三条命令都写在 ARCHITECTURE §7 里，但没有自动化。
- **失败机制**：本项目的正确性高度依赖配置（48 字段、4 产品、1 套规则库）。改配置 → 没人跑体检 → 错误配置直接进入生成物 → **产出错误文档**。
- **成立条件**：只要有一次「改完配置忘记体检」就会发生。历史上有多少次无人知道。
- **结论**：**建议修复**。配置化程度与验证体系不匹配，是本项目最结构性的风险。
- **确定程度**：【已复现】。

### 问题 3：备份尚未落地，且未演练过恢复　【已复现 + 待确认】

- **证据**（两条）：
  1. `deploy/ubuntu/部署文档.md:130` 原文是「**建议加 cron** 每日打包 `workbench/data/`」——是建议，不是已配置。
  2. `workbench/data/backup/` 只有两个文件：`workbench_20260907_232610.db`、`workbench_pre_v3_20260921_101035.db`，都是**迁移前的人工快照**，不是定时备份。
- **失败机制**：已部署到公网服务器（腾讯云），数据目录在服务器本地。若实例故障/误删/磁盘问题 → 客户项目数据、转写稿、生成物全部丢失，且无异地副本。
- **成立条件**：服务器出任何一次故障。
- **结论**：**建议修复**。另外，即使加了备份，也要问一句「**恢复成功过吗**」——没演练过的备份不算备份。
- **确定程度**：【已复现】（文档措辞 + 目录内容）／恢复是否演练过【待确认，需问部署人】。

### 问题 4：进程重启会让在途转写任务变成僵尸　【静态风险】

- **证据**：`services/audio.py:24-25` 用**内存中的 `_running` 集合**防重复提交；全仓 grep `resume|recover` 无命中；`app.py` 启动时没有扫描并恢复未完成任务的逻辑。任务状态与 `provider_job_id` 是入库的（`repo.py:292`），所以**信息足够**，但**没有人去做恢复**。
- **失败机制**：转写进行中重启服务 → 线程消失 → 数据库里该任务仍是 `running` → 页面永远轮询不到结果 → 用户只能手动重试；而腾讯云那次调用可能已经完成并计费。
- **成立条件**：转写耗时较长（实测 66 分钟音频约 2 分钟，长录音更久），重启窗口内命中概率不低。
- **结论**：建议补一个启动时的恢复动作（扫描 `running` 且已提交的任务，用 `provider_job_id` 继续轮询）。
- **确定程度**：【静态风险】——我读了代码但**没有真的重启服务验证**。若已有人在运维中遇到过，属已复现。

### 问题 5：生成物覆盖写，历史版本不可回溯　【已复现】

- **证据**：`core/generate.py:263-271`，输出文件名固定为 `adef['name'] + '.md'/.html'`，写入同一目录，无版本号、无时间戳。
- **失败机制**：规则库或模板更新后重新生成 → 旧报告被覆盖 → **无法回答「当时给客户的那份是按哪版规则算的、写了什么」**。虽然新文件内的 `meta` 记录了版本，但旧内容已不在。
- **成立条件**：规则库变更（设备管家 rules_version 1.0.0，未来必然演进）或人工重新生成。
- **结论**：建议按 `规则版本/时间戳` 归档，或至少保留上一版。对「文档会被传递给客户」的场景，这是可追溯性缺口。
- **确定程度**：【已复现】。

### 问题 6：三个负样本没有被任何测试消费　【已复现】

- **证据**：`samples/` 下有 `transcript_analog.md`、`transcript_medical.md`、`transcript_nointernet.md`、`transcript_missing.md`；grep 测试代码，只有 `tests/test_device_butler.py:413 test_low_relevance_transcript_rejected` 一条关联度测试，**其余负样本无引用**。
- **失败机制**：负样本的存在说明作者意识到「无关输入应被拒绝」，但没有测试锁定这个行为 → 改提取逻辑时可能静默失效 → 用户粘错内容也会产出一份**看起来正常的错误文档**。
- **成立条件**：任何一次提取逻辑改动。
- **结论**：低成本高收益，建议补 4 条断言测试。
- **确定程度**：【已复现】。

### 问题 7：`fire_butler` 无金标准样例　【已复现】

- **证据**：`samples/device_butler/expected.json` 与 `samples/energy_butler/expected.json` 存在且被测试消费；`samples/fire_butler/` 只有 `full.md`，**没有 expected.json`。
- **失败机制**：规则库/字段变动时，消防管家没有回归基准。
- **成立条件**：消防管家有实际使用者时才重要。
- **结论**：【待确认】——**需先确认消防管家有没有人在用**。如果没人用，这条优先级应该下调（我不替你判断产品线优先级）。
- **确定程度**：文件缺失【已复现】；是否影响业务【待确认】。

### 问题 8：provider 抽象是空壳　【已复现】

- **证据**：`providers/asr/base.py`（45 行 ABC）、`providers/storage/base.py`（35 行 ABC），无实现类；`providers/tencent_pipeline.py:7` → `from tools import tencent_asr_smoke as smoke`。
- **失败机制**：换厂商要动 `tools/` 下那个名字带 smoke 的 22KB 脚本；而 `tools/` 里的东西在所有人心里都是「可随便改删」的。抽象没隔离变化，反而多绕一层。
- **成立条件**：换厂商或改 ASR 参数时。
- **结论**：建议收编。但我把它排在日志、CI、备份**之后**——因为它不导致用户可见故障。
- **确定程度**：【已复现】。

### 问题 9：SQLite 并发 —— 第一版的判断需要修正

- **证据**：`core/db.py:11` `PRAGMA journal_mode=WAL`；`core/db.py:173` `sqlite3.connect(..., timeout=30)`（即 busy timeout 30 秒）。
- **修正说明**：我在第一版里写过「后台线程 + 单机数据库 = 迟早踩」。**这个结论下早了。** WAL + 30 秒 busy timeout 是相当合理的组合，且部署文档已明确禁止多 worker。
- **剩余风险**：`timeout=30` 意味着极端情况下写操作会阻塞 30 秒才报错；实际并发量未知。
- **结论**：**降级为待确认**。需要问：实际同时在线人数？转写线程写库频率？有无出现 `database is locked`？
- **确定程度**：【待确认】——这需要生产运行数据，我不凭技术组合下结论。

## 九、直话

1. **最值钱的资产不是代码，是两样东西**：`config/` 的三层模型（48 字段 / 4 产品 / 代码零产品名分支，我 grep 验证过），以及贯穿全项目的**保守设计纪律**（宁可留空不编造、未知模式抛错不回落、写回前再查一次 protected）。对一個「把口语变成客户文档」的系统，后者比任何性能优化都值钱。**这两样请守住。**

2. **最大的风险是可观测性为零**。系统连着两个付费 API、已部署到公网、输出会传递给客户，但**没有任何业务日志**。这意味着出问题时你既不能定位原因，也不能回答「影响了谁」，更拿不出账单争议的证据。这条我认为是最严重的，优先级高于所有架构整洁度问题。

3. **第一版评审里我把「文档与实现不一致」说成头号技术债，这次我下调了它。** 它误导的是未来的维护者，代价是未来改动的成本；而「无日志」「无备份」影响的是**现在**能不能兜住事。排序要按「误导谁、触发什么决策、损失多大」，不能按「哪个落差最显眼」。同理，「后台线程 + SQLite 迟早踩」我也撤回了——WAL + 30 秒 timeout 是合理配置，我没有证据说它会出问题。

4. **三件事做完就能毕业**：加日志、落地备份并演练恢复、加 CI。加起来 2-3 人日，比任何重构都划算。

5. **别急着上框架、换数据库、拆微服务。** 你这个规模，Flask + SQLite + 原生 JS 是对的。真正的短板在验证与可观测性，不在技术选型。

> **说明**：第 1、2、4 条是**事实判断**（有命令输出或代码行号支撑）；第 3 条是我对自己前一次评审的修正；第 5 条属于**我的偏好**（你可以有不同判断，比如团队已熟悉某框架）。
