## 1. 文档目的

在现有「粘贴文字稿 → 提取 → 核对 → 生成」的工作流中，**新增「踏勘录音文件上传 → 云端转写 → 术语矫正 → 分段提炼 → 作为后续步骤输入」的能力**，使踏勘人员完成现场工作后，仅需上传录音文件即可进入原工作流，无需自行转写和整理文字稿。

- 转写产物与粘贴文字稿在提取环节**地位等价**，下游流程不做区分

## 3. 目标场景

**主场景：** 踏勘人员在客户现场完成 1–2 小时踏勘访谈（多人对话，含寒暄、口语重复、话题跳跃），返回工位后：

1. 打开工作台，进入对应项目与产品
2. 上传手机录音文件（可能 1 个长文件，也可能多个分段文件）
3. 系统在云端完成转写，期间用户可离开页面做其他事
4. 转写完成后，用户校对文本（说话人、术语）
5. 系统自动分段提炼为结构化纪要，用户确认分段与要点
6. 后续沿用原工作流：字段提取 → 核对 → 校验 → 生成 → 打包

**关键约束：** 踏勘人员与方案人员是同一人（§16-1），全流程单人完成。因此新环节**不得增加实质性人工整理负担**——如果系统只是把"听录音整理文字稿"换成"校对 2 万字转写稿"，就没有解决问题。

## 4. 完整业务流程（改造后）

```
① 现场踏勘（1–2h 录音，手机录音笔）
        ↓
② [新增] 项目内上传录音 → 创建转写任务
        ↓
③ [新增] 云端转写（异步：提交 → 轮询 → 取回）
        ↓
④ [新增] 术语矫正（ASR 热词表 + 配置化纠错映射）
        ↓
⑤ [新增·介入点1] 转写后校文本  ← 人工确认
        ↓
⑥ [新增] 分段提炼（话题切段 → 逐段纪要 → 全局汇总）
        ↓
⑦ [新增·介入点2] 纪要后校分段  ← 人工确认
        ↓
⑧ [现有] 字段提取（source_type = audio）
        ↓
⑨ [现有·介入点3] 信息核对
        ↓
⑩ [现有] 完整性校验 → 预览 → 生成 → ZIP 打包下载
```

**与原流程的关系：** 步骤 ①–⑦ 是新增前置段；步骤 ⑧–⑩ 完全沿用现有实现，仅需扩展数据来源类型。

## 5. 功能需求

### 5.1 录音上传

| 项 | 要求 |
|---|---|
| 入口 | 项目产品页（`/p/<pp_id>/survey` 页内）新增"上传录音"入口，与现有"粘贴文字稿"并列 |
| 归属 | **不做额外确认步骤**：项目与产品归属自动继承当前页面上下文（依据需求负责人决策） |
| 支持格式 | mp3 / m4a / aac / wav / amr（覆盖手机录音常见格式）。**优先选择原生支持 m4a 直传的厂商，避免引入 ffmpeg** |
| 单文件限制 | 时长上限 **4 小时**（需求为 2h，留 2× 余量）；文件大小上限 **500MB** |
| 多文件 | 支持一次上传多个文件，视为**同一份踏勘记录的分段**；需按文件名或上传顺序确定拼接次序 |
| 断点与重复 | 同一文件重复上传时给出提示（按文件名 + 大小 + 时长指纹判定），允许强制继续 |
| 上传进度 | 前端显示上传进度；大文件上传中可离开页面，返回后状态可恢复 |

### 5.2 云端转写任务

| 项 | 要求 |
|---|---|
| 执行模式 | **必须异步**。上传后立即返回任务 ID，页面不阻塞（依据 §11.1"AI 处理中显示明确进度"） |
| 状态机 | `uploaded` → `submitted` → `transcribing` → `transcribed` → `failed`（可重试）<br>后接 `corrected` → `summarized` → `extracted` |
| 进度反馈 | 展示已耗时、当前状态、预计剩余时间（可用同类任务历史均值估算，**不得编造精确进度百分比**） |
| 失败处理 | 转写失败可单独重试，**不得影响项目内其他产品与已确认字段** |
| 结果落库 | 转写结果须**立即落库**，不得仅依赖厂商侧有效期（阿里云结果保留 72 小时、火山 TaskId 有效期 1 天） |
| 超时 | 设定上限（建议 4 小时），超时标记为失败并提示可重试 |
| 回调与轮询 | 二选一或并存；无论何种方式，**必须有轮询兜底**，避免回调丢失导致任务永久悬挂 |

### 5.3 转写结果结构化

| 项 | 要求 |
|---|---|
| 说话人分离 | 开启，支持至少 4 人区分（`speaker_id`）；说话人需支持人工重命名（如"客户方-张工""我方-PA"） |
| 时间戳 | 保留句级/段级起止时间戳，**用于"转写后校文本"环节的回听定位**，以及字段依据定位到录音位置 |
| 分段结构 | 输出结构为：`[{序号, 起止时间, 说话人, 文本, 原始置信度标识}]` |
| 原文不可变 | **转写原文为不可变基底**，任何矫正只保存"修正映射 + 矫正后文本"，原始文本必须可回溯（依据 §6.3"保留原始文字稿，后续提取和生成不得覆盖原文"） |

### 5.4 业务名词矫正（需求负责人追加要求）

**两级设计，配置驱动，不硬编码进代码（依据 §9.2 配置化边界）：**

**第一级：提交转写任务时传 ASR 热词表**
- 新建 `workbench/config/products/safety_butler/asr_terms.json`
- 内容为业务术语清单 + 权重，运行时映射为厂商热词表参数
- 高优先级术语使用厂商的"强制替换"能力（如腾讯云权重 100 的同音同调强制替换）

**第二级：转写结果后处理纠错映射**
- 同一配置文件中维护"错词 → 正确词"映射表（形如 `"消控室/消控市/消控式" → "消控室"`）
- 纠错**必须记录命中日志**（原文位置、原词、替换词），供人工复核与统计
- 厂商若更换，第二级矫正仍然有效

**初始术语表范围（首批，与真实收资项对齐）：**
消控室、点位、恒益、算力卡、机柜、交换机、周界、道闸、门禁、能耗配电、中央空调节能、维保单位、提资、踏勘、PA、项目经理

> ⚠️ 术语表初稿需业务方补充确认，标注为待确认项（见 §10）。

### 5.5 转写后校文本（人工介入点 1）

| 项 | 要求 |
|---|---|
| 页面 | 新增"转写校对"页，左/上为转写文本（可按说话人与时间浏览），支持定位回听（若音频可本地播放） |
| 主要操作 | 说话人重命名；术语与错字修正；标记段落为"与本次踏勘无关"（寒暄、闲聊）以便后续提炼时排除 |
| 关键要求 | **本环节不得要求逐字校对 2 万字**。设计目标：用户只需处理系统标记的"待确认术语"和"低置信片段"，其余默认通过 |
| 进度保存 | 与现有信息核对页一致，浏览器端自动保存（沿用 `static/app.js` 机制） |
| 可跳过 | 允许直接跳过进入下一步，跳过状态需记录 |

> **设计红线：** 若本环节耗时超过 15 分钟，则本方案未达成 §3 的目标场景，需重新设计。

### 5.6 分段提炼与纪要（人工介入点 2）

| 项 | 要求 |
|---|---|
| 目的 | 解决"2–4 万字长文本无法直接用于字段提取"的问题（当前 `core/extract.py` 为规则引擎，样例仅数百字） |
| 切段策略 | 优先按 VAD 静音边界 + 时间跨度 + 说话人切换切分；必要时辅以 LLM 话题判定。目标段长约 3–8 分钟音频对应文本 |
| 逐段产出 | `{段号, 时间区间, 话题标题, 要点列表, 涉及字段线索, 涉及产品（安全/消防）}` |
| 全局汇总 | 采用 map-reduce：逐段纪要 → 汇总为一份"踏勘纪要"，并保留每段到原文时间区间的映射 |
| 人工确认 | 展示分段列表与纪要，支持合并段、拆分段、修改标题、排除无关段 |
| 输出 | 该纪要作为字段提取的**主要输入**；原始转写文本作为**依据来源**保留 |

### 5.7 与字段提取的衔接

| 项 | 要求 |
|---|---|
| 输入源类型 | 扩展 `SurveySource`，新增 `source_type = audio`（现有为文本） |
| 提取输入 | 分段纪要（主）+ 原始转写文本（依据检索） |
| 依据可定位 | 字段的"来源片段"须可追溯到**具体时间戳区间**，便于回听核对 |
| 通道选择 | 长文本场景下 `rule` 通道（规则引擎）预计不足，需评估启用 `llm` 通道；**通道选择不得绕过 §6.4 的结构校验要求** |
| 兼容性 | 粘贴文字稿的路径**必须完整保留**且不受影响，两条输入源地位等价 |

### 5.8 字段核对（人工介入点 3）

沿用现有"信息核对"页与 `protected` 字段保护机制，**不新增环节**。需确认：重新执行提取时，对已人工确认字段的保护行为与现有实现一致（§6.3、§17 P1-1）。

### 5.9 与现有环节的兼容

- 现有 `survey_sources` 表的文字稿路径不受影响
- 项目复制、归档、删除、重新进入等行为需覆盖音频与转写结果（§6.1.4、场景 F）
- ZIP 打包的目录规则需纳入新增的转写原文与纪要（建议作为可选生成物，见 §7）

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 上传 500MB 文件不得导致服务无响应；转写期间页面操作不受阻塞；分段提炼需显示进度 |
| 密钥安全 | 密钥只从环境变量读取，**不得进入代码、前端、日志、配置文件明文**（§11.3） |
| 日志脱敏 | 日志不得记录完整转写正文；记录音频文件名时需评估是否含客户信息（§11.3） |
| 数据留存 | 音频原件与转写结果**原则上永久保留**（§16-10）；需确认对象存储侧文件的留存策略 |
| 成本可观测 | 每次转写任务记录 audio_duration 与预估费用，形成台账，避免成本失控 |
| 可测试性 | 转写 provider 接口须可注入 mock，使 `selftest.py` 无需真实调用云端即可验证全链路（§11.4） |
| 可迁移性 | 按"未来演进为多人网页"的边界设计（§16-3），上传与转写任务不得绑定单机路径假设 |

## 9. 异常与边界情况

| 场景 | 处理要求 |
|---|---|
| 音频格式不支持 / 文件损坏 | 上传阶段即校验并给出明确提示，不进入转写队列 |
| 音频时长超限或超长（>4h） | 上传前拒绝并提示；或提示需分段 |
| 转写任务失败（网络/鉴权/额度） | 分类给出失败原因与可恢复操作；鉴权失败须明确指向"检查密钥配置" |
| 转写结果为空或严重残缺 | 标记为"转写质量异常"，提示更换通道（云端↔本地）或人工粘贴文字稿 |
| 上传中断 | 支持重新上传；已完成部分不必重传（视技术可行性，否则至少给出明确提示） |
| 转写期间关闭页面 / 关闭程序 | 重新进入后可恢复任务状态；**任务不得因页面关闭而丢失** |
| 结果被厂商侧清理 | 依赖"立即落库"策略规避；若已丢失则提示重试 |
| 录音内容与当前项目不匹配 | 在"转写后校文本"环节提供"标记为无关/更换项目"的操作 |
| 多人重叠说话导致分离错误 | 允许人工合并/重命名说话人；不要求自动纠正 |
| 含客户敏感信息（监控账号密码等） | 见 §10 待确认项；未决策前**不得上传至公有云** |

## 10. 验收场景（新增）

### 场景 G：录音端到端主流程
给定一份真实 2 小时踏勘录音，用户上传后可离开页面；转写完成后依次完成转写校对、分段纪要确认、字段提取与校对，最终生成至少两种生成物并成功下载 ZIP。**全程人工操作时间不超过 30 分钟。**

### 场景 H：长文本提取有效性
给定 2 小时录音转写结果（约 2–4 万字），系统提取出的字段中，**必填项覆盖率不得低于现有短文字稿样例的水平**，且每个字段的来源可定位到具体时间戳。

### 场景 I：转写任务异常恢复
转写任务在提交后失败（如密钥错误/网络中断），用户可看到明确原因，修正后可单独重试；重试期间项目内已人工确认的字段不被覆盖。

### 场景 J：双输入源并存
同一项目下，一个产品走粘贴文字稿路径、另一个产品走录音上传路径，两者互不干扰，均可正常完成生成与打包。

### 场景 K：业务名词矫正有效性
录音中出现"消控室""恒益""点位"等术语时，矫正后的文本中该类术语的**准确率不低于 95%**，且所有纠错均可追溯到命中记录。

## 11. 待确认决策清单

### P0：阻塞实施，需需求负责人决策

| 编号 | 事项 | 为什么阻塞 |
|---|---|---|
| P0-1 | **选定转写通道与厂商**，并获取密钥 | 决定后续所有技术设计；无密钥无法开发与联调 |
| P0-2 | **是否允许录音上传至公有云**（录音含客户敏感信息：项目信息、监控账号密码、组织架构） | 若不允许，则必须走本地 FunASR 通道，架构与依赖方案完全不同 |
| P0-3 | **是否放宽"唯一 pip 依赖 flask"约束** | 云端方案需对象存储 SDK；本地方案需 torch/funasr（约 2GB+）。两条路都会打破该约束 |
| P0-4 | **提供 1 份真实 2 小时踏勘录音样本**（可脱敏） | 无真实样本则无法验证转写质量、术语矫正效果、分段策略与场景 G/H/K，开发只能盲做 |
| P0-5 | 音频原件与对象存储侧文件的留存/删除策略 | 影响数据实体设计与合规 |

## 12. 当前明确假设

- 首版**不做实时转写**（边录边转），仅支持录音文件上传（对 §4.2 的部分反转）。
- 踏勘录音为**单人使用的手机录音笔**，非多轨专业设备。
- 转写由 AI 完成，**人对转写质量与最终字段负责**；系统不承担转写错误的业务后果。
- 从录音到字段提取之间**必须存在分段提炼层**（依据需求负责人决策），不允许把 2 万字口语直接喂入字段提取。
- 转写与提炼过程**不得引入新的精确金额编造风险**（§8 铁律仅约束费用，此处沿用同一原则：不确定即标注待确认）。
- 现有粘贴文字稿的路径**完整保留**，两条输入源长期并存。
