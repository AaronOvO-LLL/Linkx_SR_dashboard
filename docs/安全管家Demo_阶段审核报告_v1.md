## 一、审核结论

**结论：有条件通过（工程实现通过，业务基线不通过）**

工程层面，开发 Agent 交付了一个可运行、可回归、配置化程度高的 Demo，77 项自测全通过，主流程与异常场景均可复现。

业务层面，**交付物跑通的是一套"自洽但未经业务确认"的假设逻辑**，与资料输入区中已有的真实业务资料存在结构性偏差。在业务基线补齐前，本 Demo 只能用于演示交互形式，**不能用于任何对客或报价场景**。

判定理由见第三、四节。

## 三、问题清单及严重程度

### 【阻塞】

#### B-1　费用单价为虚构数据，却标注为"受控价格表"

- **位置**：`config/products/safety_butler/pricing.json`
- **事实**：9 个计价项的 `price_source` 全部写作 `"受控价格表 v0.1.0"`，但该价格表在资料输入区及全项目中**不存在**。AI 摄像机 ¥1200/台、远程值守 ¥80/点位·月、驻场安全员 ¥9000/人月、平台 SaaS ¥1500/套·月 等均为假设值。
- **违反**：§8「不允许模型自由编造单价」、§18「费用不得由大模型自由编造，必须由规则、价格表或人工输入支撑」。
- **风险**：这是本次审核发现的最高风险项。系统在**形式上完全合规**（有 price_source 字段、有区间、有待确认机制），但**数据源是编造的**。形式合规会掩盖实质违规，一旦 Demo 结果被当作报价依据，即为商务事故。
- **修改要求**：二选一，且必须由需求负责人确认：
  - 方案 A：投入真实价格表，逐项替换 `unit_price` 与 `price_source`；
  - 方案 B：保留占位值，但将 `price_source` 全部改为 `"待确认·示例值（非真实报价）"`，并在费用卡片顶部加醒目声明。
- **验收方法**：`pricing.json` 中每个 `unit_price` 均可追溯到一份可指认的来源（真实价格表条目 / 人工补填记录 / 明确标注的示例值）。

#### B-2　字段模型与真实踏勘表结构性偏差

- **位置**：`config/products/safety_butler/fields.json`（44 字段，18 必填）
- **事实**：资料输入区已有真实业务资料「灵石踏勘」填报系统（S1–S4 四板块，84 个收资项）。比对结果：Demo 的 44 个字段标签与真实收资项**完全同名的仅 1 个**（建筑面积）。
- **偏差性质**：两者不是同一层信息。
  - 真实踏勘表「安全管家·监控详情」采集的是**工程接入层**参数：摄像头总数、支持协议（GB28181 等）、存储设备品牌型号、监控系统账号密码、监控机房位置、网络带宽、外网接入方式、算法接入路数、算法需求（12 类算法多选）、点位图。
  - Demo 采集的是**销售方案层**信息：客户名称、当前安全管理模式、主要问题风险、服务项、服务频次、驻场或远程、预算。
- **附带发现**：真实业务中「安全管家」是 S4 专项踏勘下的 **1/5 分组**，同级还有人行·门禁、车行·道闸、能耗·配电监测、中央空调·节能。这与需求文档 §16-8 记载的「安全、消防、能源、设备四大产品」不一致。
- **影响**：Demo 演示的提取—确认—生成闭环是成立的，但提取的是"别的东西"。若按此模型推广，后续接入真实业务时需推倒重做字段层。
- **修改要求**：将「灵石踏勘」填报系统正式纳入资料基线，逐项核对 84 个收资项，重新定义安全管家字段模型，并由需求负责人确认产品线与分组口径。
- **验收方法**：新字段模型与真实收资项逐条可映射；无法映射的字段有明确的人工确认记录。

#### B-3　生成物直接搬运口语原文，不具备对客可用性

- **位置**：`value_card/价值卡片.md`、`cost_estimate/费用估算卡片.md`
- **事实**：
  - 价值卡片「客户现状」原文照搬转录口语，含大量脏数据：`"现在安全管理这块说实话比较原始；就是门口两个保安轮班，；保安在门房根本发现不了"`（连续分号、半截句）。
  - 费用卡片「客户预算线索」：`"商务上，预算大概二十万左右一年，按月付或者按季付都行"`。
  - 费用卡片「本估算不含」：`"驻场暂时不需要，说现在预算紧"`。
- **风险**：这些文件在流程中的定位是交付客户的材料，当前内容是内部速记。直接对外发出将造成专业形象与客户信任损失。
- **修改要求**：在提取值与生成物之间增加「口语转书面」改写层；建立对客材料的禁用词/脏数据清洗规则（连续标点、口语助词、客户内部措辞）。
- **验收方法**：生成物中不出现转录口语特征（"说实话""他们""呢""吧"、连续分号、半截句）；每条结论可指向结构化字段而非原文片段。

### 【重要】

#### I-1　待确认项文案嵌套重复
费用卡片「待确认项」输出：`单价待确认（待确认（需评估接口工作量））`。属于字符串拼接缺陷，影响专业观感。

#### I-2　输出格式未覆盖 Word / Excel / PDF
当前仅 md / html / csv。需求 §17 P0-4 明确列为待确认项，商务交付场景通常需要 Word 与 Excel，建议尽快确认。

#### I-3　§17 P1 五项待确认均无决策记录
包括：重新解析时的合并口径、复制是否含原文与生成物、删除方式、密码维护入口、多产品文字稿共用或独立。代码中已做了技术选择（保护人工值、复制含原文、软删除、页面改密），但**均未经过业务确认**，属"以技术便利代替业务决策"，违反 §0.2-7。

### 【建议】

#### S-1　敏感数据脱敏缺失（§11.3）
真实收资项包含「监控系统账号密码」等高敏字段，建议在展示与日志侧增加掩码与脱敏策略。

#### S-2　照片能力
真实填报系统中 `photo` 出现 8 处、「拍照」10 处，照片是现场收资核心。首版按需求不做属合理范围，但建议在路线图中明确。

#### S-3　真实表的「痛点」字段未对应
真实填报系统存在 `painEx`（痛点示例）结构，与价值卡片的"核心问题"高度相关，建议纳入字段模型。

## 四、尚未解决的风险、假设与待决策事项

1. **产品口径待澄清**：安全、消防、能源、设备四产品（需求文档）vs 监控、门禁、道闸、能耗、空调五专项（真实系统）——以哪个为准？
2. **价格数据来源待定**：是否有可投入的真实价格表？若无，Demo 的费用估算是否只做"结构性演示"并全程标注示例值？
3. **业务资料是否已被正式读取**：资料输入区 README 约定用户说"资料放好了"后才读取归类。目前该指令似未下达，导致已存在的真实资料未被纳入基线。
4. **Demo 定位待确认**：是继续作为"交互形式演示"（当前状态可用），还是要升级为"业务可用原型"（需补 B-1/B-2/B-3）？
