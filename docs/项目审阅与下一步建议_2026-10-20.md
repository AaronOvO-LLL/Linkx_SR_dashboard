## 已验证的问题，按建议处理顺序排列

### 1. P1：设备管家已有数据时，核对页返回 500

位置：`workbench/templates/review.html:110`、`:111`。

模板遍历 `selected_category.value.items`，但该值是字典，Jinja 优先取到了字典的 `items` 方法，实际异常为 `TypeError: 'builtin_function_or_method' object is not iterable`。空白页可能正常，选中了有效空间类别、已有设备行后触发。

现有测试 `test_scenario_a_full_flow_to_xlsx` 和 `test_scenario_g_state_survives_reentry` 均复现 500。这会直接阻断录入后的核对和重新进入。

建议明确按字典键读取 `['items']`，同时检查两个引用位置。验收：提取后进入核对页、退出后重进、含历史设备值的项目都正常。

### 2. P1：字段已修改，旧报告与旧 ZIP 仍被当作可用结果

位置：`services/artifacts.py:62`、`:80`，`services/survey.py:88`，`core/generate.py:250`，`core/packaging.py:25`，文件下载路由。

隔离复现：完整填写资产管家 → 生成报告及 ZIP → 修改客户名称 → 当前校验仍为 True → 报告下载返回 200，但内容与修改前完全相同，不含新名称；旧 ZIP 下载同样返回 200。

原因：下载前只检查当前字段是否合法；`latest_current_export` 只比较生成物 key 是否仍在当前配置里。没有比较字段修订、输入来源、模板和规则版本。直接再次打包也会复用已经成功生成的旧文件。

此外，Markdown/HTML 输出覆盖同一路径；Excel 名称通常只有日期；ZIP 名称精确到分钟。重新生成会覆盖原文件，同一分钟打包也可能覆盖相同路径，数据库中的多条记录不等于保留了多份历史文件。

建议作为一个完整主题处理：

1. 每次字段或项目生成相关信息变化时更新数据修订号。
2. 一次生成先取得同一份输入快照，所有选中材料使用这份快照。
3. 生成记录保存数据修订、字段/文档模板版本、规则版本及来源 ID。
4. 修改后标记旧结果为“需重新生成”；页面、单文件下载、打包和 ZIP 下载使用相同判断。
5. 文件按生成批次保存，先写临时文件再原子替换，历史版本明确可识别。

验收：修改一个关键字段后，全部出口都提示重新生成；重新生成结果包含新值；旧版仍能按历史版本追溯，且不会被标为最新结果。

### 3. P1：能源管家的设备词表与样例、提取结果不一致

位置：`config/field_packs/energy_survey.json:150`、`:171`，`samples/energy_butler/full.md`、`expected.json`，`tests/test_energy_butler.py:66`。

当前候选项为“制冷主机”“冷冻泵”，样例与期望值却使用“冷水主机”“冷冻水泵”。专项测试完整填写后，三行设备均被判为“不在候选范围内”，因此生成流程失败。规则提取测试仍能通过，是因为它只与旧期望值比较。

配置还同时包含“板式换热器两侧进出水（如有）”选项与排除包含“板式换热器”的校验，存在业务口径冲突；这一项需要业务确定是否应支持，不能只为测试变绿而放宽校验。

建议统一标准设备名和同义词映射，兼容历史值，并同步选项、提取提示、规则通道、样例、期望值和测试。验收要从原文走到校验和 Excel，不能只验证提取 JSON。

### 4. P1（对客输出前）：待确认状态与“已人工确认”承诺不一致

位置：`core/validate.py:44`，`services/artifacts.py:32`，`core/packaging.py` 的 `_readme`。

隔离复现：把已完整填写字段改成 AI 来源、低置信度、`pending_confirm` 状态，校验仍通过，材料生成仍成功。当前校验主要检查是否填写、类型和业务准入，不要求确认状态。

允许输出待核对草稿可以是合理产品选择，但 ZIP 的 README 无条件写着“所有内容均经人工确认后生成”，与实际机制不符。

建议明确区分草稿和确认版：草稿标出待确认项；确认版要求关键字段或整份材料显式确认，并绑定确认时的数据版本。任何后续修改都使该确认失效。系统自动生成的时间等字段可按配置豁免，不必机械要求每项手工点击。

### 5. P2：模型返回合法 JSON、结构却不正确时，异常未被完整处理

位置：`core/extract.py:687`—`:705`，`services/survey.py:68`。

使用模拟 HTTP 响应，分别返回 `{"fields":["unexpected"]}` 和 `{"fields":{"asset_customer_name":"unexpected"}}`，两者均触发未转换为 `ExtractionError` 的 `AttributeError`。

JSON 解析位于异常处理块内，但后面的 `fields` 与单字段对象没有类型验证。服务层只捕获 `ExtractionError`；遇到此类返回时可能响应 500，并让提取记录停在 running。当前两个 LLM 契约测试只覆盖单值归一化，不能覆盖完整响应。

建议先检查顶层对象、fields 对象、单字段对象、quote 和 confidence 类型，统一转换业务错误；保证每次已登记的提取都有成功或失败终态。补充畸形 JSON 结构、空 choices、空内容和错误引用测试。无需真实模型调用即可覆盖。

### 6. P2：彻底删除项目后，ZIP 实体文件仍留在磁盘

位置：`core/repo.py:136`。

隔离复现：生成资产报告与 ZIP → `purge_project` → 项目查询为空，但 ZIP 路径仍存在。代码清理了生成目录、录音目录及导出数据库记录，没有清理该产品在 `EXPORT_DIR` 下的目录。

建议将导出目录纳入删除生命周期，并记录清理失败。还应单独验证删除中的后台任务，避免项目已删除、线程仍在继续处理。复现仅针对本机导出文件，不代表已验证云端对象清理情况。

## 工程与运维：值得补齐，但不必大改架构

### 发布与回归

当前仓库没有 `.github` CI；资产管家、聊天 provider/service、前端文件等仍有未跟踪文件，已有 13 个跟踪文件处于修改状态。这是工作区现状，不代表文件已丢失；但只按当前提交部署，不能还原本机全部能力。

建议先形成一个完整、可复现的版本：检查文件清单、排除密钥与运行数据、记录版本和变更，建立配置检查 + 全量单测 + selftest 的统一命令和发布门槛。当前“自检全绿但专项测试失败”说明不能只跑一个脚本。

### 付费调用、并发与任务恢复

- 当前 ASR 已有页面触发恢复：项目概览、状态接口和预览页都会尝试拉起任务；已有 provider_job_id 时继续轮询。因此旧评审中“重启后完全无人恢复”的判断不应原样沿用。
- 仍有一个静态风险：云端已经接收 submit、但进程尚未把 provider_job_id 写入数据库时崩溃，恢复可能重复提交。内存 `_running` 不能覆盖这个窗口；重试还会直接清掉已有任务 ID。建议保留 attempt 和不确定状态，重试前区分继续查询与重新计费提交。
- LLM 提取仍在 HTTP 请求内同步执行，且同一产品没有持久化的提取互斥或输入修订检查；并发提取可能出现后完成的旧请求覆盖新结果。人工保护在写回前重查是好的基础，但检查与写入不是原子操作。建议在确定需要多人使用后补条件写入、产品级任务状态和幂等控制。
- 暂时保留单进程 Waitress + SQLite。不要为了这些问题立即引入微服务或完整任务集群。

以上并发和云端提交窗口属于静态分析，本次没有做真实崩溃、重复计费实验。

### 备份、可观测性与访问控制

- 仓库部署文档中的备份仍是建议命令；本次不能判断线上是否另有计划任务。应核实是否有异地备份，并在隔离目录完成一次恢复。SQLite WAL 模式下应使用一致性快照方式，且将录音、凭据、输出文件与数据库的恢复关系讲清楚。
- core/services/providers 未见结构化业务日志，生成异常主要靠 traceback。先补请求/任务编号、项目/产品、阶段、耗时、状态、错误类别；不记录密钥和客户全文。
- 分部共享口令适合受控试用；多人正式使用前需确认个人身份、操作审计、登录限流、改密后的会话失效。普通业务写接口未采用聊天接口已有的 CSRF token 校验，需要统一策略；SameSite=Lax 是已有保护的一部分，不能据此断言当前已发生跨站攻击。
- 生产密钥校验、密码哈希、Waitress/systemd/nginx 配置已经存在。不能再把旧报告中的“尚无这些能力”当成当前事实。实际 HTTPS、默认口令、备份和防火墙状态需在线上另行核实。

### 姜子牙聊天的下一步

本地会话隔离、请求防重复、纯文本展示、敏感凭据不送前端均已有措施；9 项专项测试在全量测试中通过。

当前限制写得比较清楚：服务重启清空聊天；前端聊天不自动读取项目，不自动修改字段；所有上游客户端默认使用同一个配置的 GC_USER_ID。按 messageId 区分会话不等于已经建立用户身份体系，真实多人隔离需要平台侧验证。

因此下一步不宜立即让聊天承担自动写表或自主生成承诺。若要接入业务，先做“用户明确选择当前项目资料 → 只读问答 → 引用具体字段/依据”，再考虑受确认保护的修改建议。

## 接下来适合做什么

### 第一批：先让已有能力稳定

1. 修设备核对页 500；统一能源设备词表及历史值处理。
2. 给生成物加数据修订与过期判断，统一全部下载出口；明确草稿/确认版口径。
3. 修模型响应结构处理和导出文件清理。
4. 跑全量回归并整理一个可复现的提交。设备名和确认规则需要先明确业务口径；结果快照与历史归档应独立安排，避免与快速修复混成一次大改。

验收不是“页面能打开”，而是“改了关键事实就不能再把旧文件当最新版下载，未确认内容也不会被描述为已经确认”。

### 第二批：沿 10 月计划形成 PPT 的开发契约

季度计划目标为 10 月确认模板、11 月跑通自动 PPT、12 月场景扩展与比干联调。当前后端实际输出为 Markdown/HTML/Excel/ZIP；未见 PPTX 渲染器和比干业务接口实现。

本周（10/19—10/25）最有价值的产品交付物是：

- 一份业务确认的脱敏完整样稿，选择已有资料齐备、规则明确的单个场景。
- 一张“页面 → 输入字段 → 固定/动态内容 → 缺失处理 → 确认人”表。
- 三个验收案例：标准资料、资料缺失、长文本/多设备行。
- 明确比干调用方向、身份和权限、任务创建/查询/下载契约，以及真实接口联调的负责人和时间。

模板与字段合同明确后，先验证标题、正文、设备表和图片页等少量关键页面，生成实际可编辑的 PPTX，再接入现有生成服务。PPT 的布局、分页、长文本和图片适配应放在独立 renderer 中，不把版式判断塞入提取或路由。

### 第三批：用业务试用决定继续投入的方向

找 2—3 位实际使用者，用 3 个不同案例独立完成流程。记录关键字段错误、专家复核耗时、反复补资料次数、需要线下改多少页，以及是否主动使用第二个项目。

不要只用字段数量、产品数量或演示是否流畅衡量进展。如果 PPT 仍需专家重写大部分内容，应优先修正字段与内容契约；如果内容正确、主要卡在资料不齐，则优先收资引导和缺失提示。
